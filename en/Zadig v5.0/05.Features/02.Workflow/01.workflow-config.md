Workflows provide flexible orchestration capabilities. You can freely arrange workflow processes and customize execution steps. This article describes the related configuration options.

## Creation Methods
### Create a Blank Workflow

Enter a project and click Create Workflow. Zadig provides two configuration modes: `GUI` and `YAML`.

## GUI Configuration

### Basic Information

Basic information includes the workflow name, identifier, and description:
- `Workflow Name`: Supports Chinese characters, uppercase and lowercase letters, numbers, and special characters. It must be unique within the project and can be modified.
- `Workflow Identifier`: Supports uppercase and lowercase letters, numbers, and hyphens. It must be globally unique and cannot be modified.
- `Description`: Describes the workflow details and is displayed on the workflow details page.

![workflow_config](./_images/config/04.png)

### Stages

Click `+ Stage` to add a new stage configuration.

![workflow_config](./_images/config/05.png)

Parameter description:
- `Stage Name`: The stage name must be unique within the same workflow.
- `Concurrent Execution`: When enabled, multiple jobs configured in this stage run concurrently.

![workflow_config](./_images/config/06.png)

Stages support two execution modes: `Automatic` and `Manual`. Manual execution allows you to specify stage executors and re-enter job parameters during execution.

### Jobs
Click `+ Job` under a stage to add a job configuration. For supported job types and detailed configuration, see [Workflow Jobs](/en/Zadig%20v5.0/project/workflow-jobs/).

## YAML Configuration

### Configuration Description

You can define a workflow using a YAML file. The overall YAML structure is described below:

```
display_name: <workflow name>       // Required. Unique within the project. Supports Chinese characters, uppercase and lowercase letters, numbers, and special characters.
name: <workflow identifier>         // Required. Unique within the project. Supports uppercase and lowercase letters, numbers, and hyphens.
stages:                            // Required. Multiple stages are executed in sequence.
  - <stage 1 configuration>
  - <stage 2 configuration>
  - <more stage configurations...>
project: <project name>            // Required.
description: <workflow description>
multi_run: <optional: true/false>  // Whether multiple workflow tasks can run in parallel when the workflow is triggered multiple times simultaneously. Default: false.
```

The detailed configuration of each stage is as follows:

```
name: <stage name>               // Required.
parallel: <optional: true/false> // Whether multiple jobs in this stage can run concurrently. Default: false.
jobs:                            // Required.
  - <job 1 configuration>
  - <job 2 configuration>
  - <more job configurations...>
```

Currently, two built-in job types are available: build and deploy. The detailed configuration of a build job is as follows:

> Build variables set in YAML take effect only when related build variables are configured in the specified build.

```
name: <job name>                     // Required.
type: zadig-build                    // Required. Set to zadig-build.
spec:                                // Required.
  docker_registry_id: <image registry ID>
  service_and_builds:                // Build information of service modules. Multiple service modules can be configured.
    - service_module: <service module name>
      service_name: <service name>
      build_name: <build name>
      key_vals:                      // Build variable information. String and choice variables are supported. See the string and choice examples below.
        - key: username              // Build variable name.
          value: Zadig               // Build variable value.
          is_credential: false       // Whether the value is encrypted. Default: false.
          type: string
        - key: password
          value: v1
          is_credential: false
          type: choice
          choice_option:             // Options for the choice variable.
            - v1
            - v2
    - service_module: <service module name>  // More service module build information.
      service_name: <service name>
      build_name: <build name>
      ...
```

The detailed configuration of the built-in deploy job is as follows:

```
name: <job name>                     // Required.
type: zadig-deploy                   // Set to zadig-deploy.
spec:
  env: <deployment environment>      // Required.
  source: <service image source used for deployment>  // Required. Options: runtime (runtime input) / fromjob (output from another job).
  job_name: <job name>               // Required when source is fromjob.
```

### YAML Example

Take the following workflow configuration as an example:

1. The first stage contains a build job and builds two services (`myapp-1` and `myapp-2`) in parallel.
2. The second stage contains a deploy job and uses the image artifacts from the build job above to deploy the `pre-release` environment.

The corresponding complete YAML configuration example is as follows:

```
name: pre-release-deploy
display_name: pre-release-deploy
stages:
  - name: build
    parallel: true
    jobs:
      - name: build-myapps
        type: zadig-build
        spec:
          docker_registry_id: 6247eb0832a15f910118318c
          service_and_builds:
            - build_name: simple-service-build-nginx-1
              key_vals:
                - is_credential: false
                  key: username
                  type: string
                  value: admin
                - is_credential: false
                  choice_option:
                    - v1
                    - v2
                  key: password
                  type: choice
                  value: v1
              service_module: myapp-1
              service_name: a
            - build_name: simple-service-build-myapp-2
              service_module: myapp-2
              service_name: b
  - name: deploy
    jobs:
      - name: deploy
        type: zadig-deploy
        spec:
          env: pre-release
          job_name: build-myapps
          source: fromjob
project: simple-service
description: pre-release environment deployment
multi_run: false
```

## Variables

Workflows provide rich variable capabilities to support parameterized workflow configuration and information transfer among jobs, stages, workflows, and projects.

### Built-in Variables

| Variable Source | Variable | Description |
|------|---------------------------------------------------|-----------------------------------------------------|
| Project |  <span v-pre>`{{.project}}`</span>                | Project name |
| Workflow |  <span v-pre>`{{.workflow.name}}`</span>           | Workflow identifier |
|  |  <span v-pre>`{{.workflow.task.id}}`</span>        | Workflow task ID, for example `1` |
| |  <span v-pre>`{{.workflow.task.creator.id}}`</span>   | Username of the workflow task executor, for example `admin` |
| |  <span v-pre>`{{.workflow.task.creator}}`</span>   | Nickname of the workflow task executor, for example `admin-nickname` |
| |  <span v-pre>`{{.workflow.task.is_release_plan_trigger}}`</span>   | Whether the workflow task is triggered by a release plan, for example `true` |
| |  <span v-pre>`{{.workflow.task.timestamp}}`</span> | Unix timestamp when the workflow task is created, for example `1686642562` |
| |  <span v-pre>`{{.workflow.task.datetime}}`</span> | Workflow task creation time, for example `2026-04-17 18:00:00` |
| Build Job | <span v-pre>`{{.job.<job name>.SERVICES}}`</span> | Set of service modules selected for the build job<br>The variable value is in the form of `aslan/zadig,zadig-portal/zadig` (service module name/service name) |
| | <span v-pre>`{{.job.<job name>.BRANCHES}}`</span> | Set of branch information for the first repository corresponding to the service modules selected for the build job<br>The variable value is in the form of `feature1,feature2,feature3` |

| | <span v-pre>`{{.job.<job name>.GITURLS}}`</span> | Set of first repository information corresponding to the service modules selected for the build job. The variable value is in the form of `https://gitlab.com/group1/repo1,https://gitlab.com/group2/repo2` (code source URL/organization name or username/repository name) |
| | <span v-pre>`{{.job.<job name>.<service>.<service module>.COMMITID}}`</span> | Commit information of the first repository of the specified service module |
| | <span v-pre>`{{.job.<job name>.<service>.<service module>.BRANCH}}`</span> | Branch information of the first repository when the service module is specified |
| Deploy Job | <span v-pre>`{{.job.<job name>.envName}}`</span> | Deployment environment |
| | <span v-pre>`{{.job.<job name>.IMAGES}}`</span> | Set of images of deployed service modules<br>The variable value is in the form of `image1:tag1,image2:tag2` |
| |<span v-pre>`{{.job.<job name>.VERSION_NAME}}`</span> | Version name selected during deployment |
| Image Distribution Job | <span v-pre>`{{.job.<job name>.IMAGES}}`</span> | Set of target images of distributed service modules<br>The variable value is in the form of `image1:tag1,image2:tag2` |

### Custom Variables

Workflow variables are divided into global variables and job variables. Global variables are configured as shown below, and custom variables in jobs are configured in the corresponding jobs.

<img src="./_images/config/07.png" width="400">
<img src="./_images/config/08.png" width="400">

Variable description:

- `Type`: Supports string, multi-line text, single choice, multiple choice, file, code repository, image, and [dynamic variable](/en/Zadig%20v5.0/workflow/dynamic-variable/).
  - `Code Repository` is available only in workflow global variables.
  - `Image` is available only in general script execution.
- `Key`: The key of the custom variable.
- `Value`: The value of the custom variable. Runtime input and fixed value are supported. For details, see [Variable Assignment Methods](#variable-assignment-methods).

### Variable Assignment Methods

Click the small icon on the right side of a variable to assign a value. The assignment methods are described below:

- `Runtime Input`: Specify the variable value when running the workflow.
- `Fixed Value`: Set a fixed value for the variable. The variable is not visible on the workflow execution page, and no value needs to be assigned during execution.
- `Global Variable/Other Job Output`: Use a global variable or a variable output from another job for assignment. During workflow execution, global variables are rendered automatically to transfer variables between different jobs.
  - Supported global variables include [Built-in Variables](#built-in-variables) and [Custom Variables](#custom-variables).
  - To use `Other Job Output`, configure output variables for the job first. See [Configure Output Variables](#variable-passing).

![workflow_config](./_images/config/09.png)

Global variables can be used in two ways:
1. Use them as shell environment variables in build, code scan, test, and general script execution jobs.
2. Define a custom variable in a job, set the assignment method to `Global Variable/Other Job Output`, and select the corresponding global variable.

### Variable Passing

Variables can be passed between different jobs. The process is as follows:

1. Declare the variables to be output in the advanced configuration of the upstream job.
2. Use the variable in the downstream job through `Global Variable/Other Job Output`.

**Configure Output Variables**

Output variables can be configured in build, test, code scan, and general script execution jobs. The output variable formats for different jobs are as follows:
- Build job: <span v-pre>`{{.job.<job name>.<service name>.<service module name>.output.<variable name>}}`</span>
- Test job: <span v-pre>`{{.job.<job name>.<test name>.output.<variable name>}}`</span>
- Code scan job: <span v-pre>`{{.job.<job name>.<code scan name>.output.<variable name>}}`</span>
- General script execution: <span v-pre>`{{.job.<job name>.output.<variable name>}}`</span>

Taking a build job as an example, add an output variable in the advanced configuration and enter the variable name.

:::: tip
1. The added variable can come from a custom variable in the build configuration or a variable set in the build script, such as `export key=value`.
2. By default, the system outputs the `IMAGE` and `PKG_FILE` variables from the build, which represent the service image name and artifact file name respectively.
::::

![workflow_config](./_images/config/10.png)

**Use Output Variables**

For jobs that support the `Global Variable/Other Job Output` assignment method, see [Configuration Methods Supported by Different Jobs](/en/Zadig%20v5.0/project/workflow-jobs/#configuration-methods-supported-by-different-jobs).<br>
Taking a custom variable in general script execution as an example: when assigning a value to the variable in general script execution, set the assignment method to `Global Variable/Other Job Output` and select the output variable configured in the upstream job. This passes variables between different jobs.

## Job Scheduling Policy

### Execution Policy

![run_job](./_images/config/13.png)

- **Execute by Default**: Jobs configured to execute by default are selected by default when `Run Job` or `Configure Trigger` is used. Users can choose not to execute them.
- **Do Not Execute by Default**: Jobs configured not to execute by default are not selected by default when `Run Job` or `Configure Trigger` is used. Users can choose to execute them.
- **Force Execute**: Jobs configured for forced execution must be executed when `Run Job` or `Configure Trigger` is used. Users cannot choose not to execute them.

### Execution Conditions

![run_job](./_images/config/14.png)

- **All Upstream Jobs Succeeded or Skipped**: Execute when all upstream jobs succeed or are skipped.
- **Execute When Conditions Are Met**: Execute when the configured conditions are met.
- **Do Not Execute When Conditions Are Met**: Do not execute when the configured conditions are met.

Condition configuration:
- Supports two matching modes: `Meet All Conditions` and `Meet Any Condition`.
- Supports built-in variables and custom variables. Operators include: `Equals`, `Not Equals`, `Contains`, `Not Contains`, `Starts With`, `Does Not Start With`, `Ends With`, and `Does Not End With`.

### Failure Policy

![run_job](./_images/config/15.png)

- **Mark as Failed**: When the job fails, the workflow stops and is marked as failed.
- **Ignore Failure**: When the job fails, the workflow continues.
- **Manual Confirmation**: When the job fails, manual confirmation is required to decide whether to `Skip` the job or `Stop` the workflow.
- **Retry on Failure**: When the job fails, it can be retried automatically based on the configured retry count.

## Trigger Configuration

Configure triggers for a workflow. When an event that meets the trigger conditions occurs, the workflow is automatically triggered. Git triggers, timers, JIRA triggers, Feishu Project triggers, and general triggers are supported. For details, see [Workflow Triggers](/en/Zadig%20v5.0/project/workflow-trigger/).

<img src="./_images/config/16.png" width="400">
<img src="./_images/config/17.png" width="400">

### Git Trigger

Parameter description:

- `Repository`: The code repository whose trigger events need to be monitored. Different code sources correspond to different trigger events.
- `Target Branch`: The base branch when submitting a pull request. Regular expressions are supported. For syntax, see [Regexp Syntax](https://pkg.go.dev/regexp/syntax@go1.17.3#hdr-Syntax).
- `Trigger Event`: Specifies the Webhook event that triggers workflow execution. Available events are:
    - `Push commits`: Triggered by push commit events (merge operations). Changes to the `description` field in the code repository are filtered and do not trigger workflow execution.
    - `Pull requests`: Triggered when a pull request is submitted.
    - `Push tags`: Triggered after a tag is created.
- `Trigger Policy`: Automatic cancellation is supported for `Push commits` and `Pull requests` events. If you want only the latest commit to trigger execution, this option automatically cancels earlier running tasks in the queue.
- `Files/Directories`: By setting files and directories, you can monitor file and directory changes. When files or directories change (created, modified, or deleted), the workflow is triggered. You can also ignore changes to corresponding files or directories so that the workflow is not triggered.

Take the following repository file structure as an example:
    
``` bash
├── reponame  # Repository name
  ├── Dockerfile 
  ├── Makefile
  ├── README.md   
  ├── src        
    ├── service1/
    ├── service2/
    └── service3/
```
| Trigger Scenario | File/Directory Configuration |
|----|------------|
| Any file is updated | `/` |
| Files other than `*.md` are updated | `/`<br>`!.md` |
| Files outside the `service1` directory are updated | `/`<br>`!src/service1/` |
| Any file in the `service1` directory is updated | `src/service1/` |
| Files in the `src` directory are updated, excluding files in the `service1` directory | `src`<br>`!src/service1/` |

### Timer

By configuring a timer, you can run workflows periodically. Currently, workflows support the following timer modes:
- Scheduled Loop: Execute a workflow at a specified time, for example, every day at 12:00 or every Monday at 10:00.
- Interval Loop: Execute a workflow periodically, for example, every 30 minutes.
- Cron Expression: Use a standard Linux Cron expression to configure timers flexibly, for example, `"45 4 1,10,22 * *"` executes a workflow task at 4:45 on the 1st, 10th, and 22nd day of each month.

#### Scheduled Loop

Procedure:
- Click the add button to add a scheduled loop entry, and select the cycle and time point.
- Set workflow task parameters. The workflow runs with the configured parameters.

![workflow](./_images/config/18.png)

#### Interval Loop

Procedure:

- Step 1: Click the add button to add an interval loop entry, and select the interval and interval unit.
- Step 2: Set workflow parameters. The workflow runs with the configured parameters.

![workflow](./_images/config/19.png)

#### Cron Expression
Procedure:

- Step 1: Click the add button to add a Cron expression entry and enter the Cron expression.
- Step 2: Set workflow parameters. The workflow runs with the configured parameters.

![workflow](./_images/config/20.png)

## Notification Configuration

Currently, workflow notifications can be sent to email, Feishu, WeCom, DingTalk, and Webhook. For detailed configuration parameters, see [IM Status Notifications](/en/Zadig%20v5.0/workflow/im).

![workflow_config](./_images/config/21.png)

Notification messages include the execution status of all jobs in the workflow. For build, deploy, and test jobs, the name rules in notifications are as follows:

- Build job: service name-service module name-build job name
- Deploy job: service name-deploy job name
- Test job: test name-test job name-random string

## Execution Concurrency
Set the concurrency in `Advanced Configuration` > `Run Policy`. Multiple workflow tasks generated by multiple workflow triggers run concurrently, improving workflow execution efficiency.

After disable mode is enabled, the workflow cannot be executed, either manually or through triggers.

You can enter remarks when running a workflow, making it easier to view workflow execution notes later. Required-at-runtime is supported. After it is enabled, remarks must be entered when running the workflow.
